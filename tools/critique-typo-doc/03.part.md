## 3. H 级问题清单

分级：**H1** = 达标线以下且影响全部用户；**H2** = 达标线以下但影响部分路径/页面；**H3** = 有明确改进空间。

每条给出：**证据（实测数值）→ 改成什么值 → 为什么**。

### H1-1　`auto` 主题下代码高亮 30/30 token 不达 AA（keyword 仅 2.85:1）

**证据**
- 结构根因：`site.css:436-442` 的 7 条 `html[data-theme="dark"] .hljs-*` 规则**不匹配** `data-theme="auto"`；而 `site.css:29-40` 只为 auto 换了 `:root` 令牌。
- 实测（`p3`/`p14`）：auto+深色下 keyword `#a626a4` on `#171a1f` = **2.85:1**；30 个 token 全部 2.85–4.36，**0 个达标**；同页面 light 为 5.92、dark 为 8.96。
- 这是**默认路径**：`index.html` 的 `<html data-theme="auto">`。

**改成什么**
把 dark 的 hljs 规则复制一份到 auto，包进媒体查询：

```css
@media (prefers-color-scheme: dark){
  html[data-theme="auto"] .hljs-comment{ color:#8b95a5 }
  html[data-theme="auto"] .hljs-keyword{ color:#d2a8ff }
  /* …其余 5 条同上，见 §4 完整代码… */
}
```

**为什么**：这是唯一「用户什么都没做就踩到」的对比度缺陷，且修复**零风险**——实测补丁后 auto 从 7/7 失败 → **0/7**（keyword 2.85 → 8.96），dark 路径数值**完全不变**（5.76/8.96/11.35 原样）。WCAG 1.4.3 要求 4.5:1。

### H1-2　正文行宽 98.4–110ch，超 Bringhurst 上限 31–47%

**证据**
- `capCh` = **110**（949px，无 TOC）/ **98.4**（849px，有 TOC）；`max` 实测最长行 98.4–107.6ch。
- 全站唯一行宽约束是 `.hero p{max-width:76ch}`（`site.css:300`），只管落地页两段。
- 唯一「限宽」的 `.content{max-width:1000px}`（`site.css:505/544`）实际是**容器封顶**，不是 measure：1000 − 51.2 内边距 = 948.8px = 110ch。

**改成什么**
```css
@media (min-width:768px){
  .article > :is(p,ul,ol,blockquote,dl),
  .article li > :is(p,ul,ol){ max-width:40rem }   /* 640px = 74.2ch = 40 全角 */
}
```
只封「行文块」，**不封代码块/表格/图片**（让它们保持整列宽，避免把 13 个代码块里的 7 个推进横向滚动）。

**为什么**：74.2ch 落在 Bringhurst 75 内侧，同时 40 全角正好是中文经验上沿。实测：1440 下正文 98.4 → **70.5ch**（38rem 时）/ **74.2ch**（40rem 时），且**代码块滚动数不变**（5/13，与基线一致）。相较「整列 40rem 居中」方案，本方案代码块滚动从 5/13 升到 **7/13**，故**只封行文块**更优。

### H1-3　「键值配置参考」内容族整体缺标题：5 页 90299 字符零 h2，另 1 页 31 个 h5 被降级

**证据**（全站 144 URL 实测 `p25` + 逐页渲染验证 `p23`）

- 141 个正文页中，**42 页 `.article` 内 `h2 = 0`**；其中 36 页字符 <3000（索引页，合理），**6 页字符 >3000（真问题）**：

| 页面 | 字符 | h2/h3/h4 | h5 | li | 页高 |
|---|---|---|---|---|---|
| `world-configuration` | 36260 | 0/0/0 | 0 | 273 | 16180 |
| `spigot-configuration` | 20362 | 0/0/0 | 0 | 179 | 9858 |
| `global-configuration` | 17748 | 0/0/0 | 0 | 127 | 7834 |
| `server-properties` | 11122 | 0/0/0 | 0 | 69 | 4122 |
| `bukkit-configuration` | 4807 | 0/0/0 | 0 | 37 | 2389 |
| `cli-arguments` | 3925 | **0/0/0** | **31** | 0 | 3857 |

- 前 5 页合计 **90299 字符 = 全站正文的 12.5%**，**零标题**。
- `cli-arguments` 有 31 个标题但**全在 h5**：渲染实测 **15.2px / 700 / #5c6470（5.98:1）**，而正文是 16px / 400 / #1c1f26（16.49:1）——标题**比正文更小、更淡**，扫视时不像标题。
- `world-configuration` 的 `li` 深度 `{1:18, 2:92, 3:94, 4:48, 5:17, 6:4}`，6 层 × 24px = 144px 缩进；320 下正文列 288px 只剩 **144px ≈ 9 全角字**。
- 双验：`measure.json` 的 DOM 计数与 `tools/critique-typo-counts.js` 的标签计数**都为 0**，非量尺漏采。

**改成什么**

```css
/* ① 深层列表缩进收敛：6 层 144px → 96px */
.article li li li :is(ul,ol){ padding-left:1em }
```

② **`cli-arguments` 的 31 个 `<h5>` 提升为 `<h3>`**（构建层，非 CSS）。
③ **前 5 页按 YAML 顶层键生成 `<h2>`、子键生成 `<h3>`**（构建层，查 `build-site.js` 对配置类源结构的标题映射）。

**为什么**：这是**严重程度高于行宽**的问题。行宽让人「读得累」，而 90299 字符零标题 + 6 层嵌套 + 320 下 77 屏，让人**根本找不到**。基准：长文每 500–1500 字符应有可扫描标题。

> **注意**：这不是「某一页写得不好」，而是**「键值配置参考」这一整个内容族的构建映射缺失**（6 页全中，模式一致）。修 CSS 缩进能让 320 下从 9 全角恢复到 12 全角，但**标题必须由构建层补**，CSS 无能为力。

### H2-1　`1025–1199` 区间正文只剩 50.3–63.8ch（`max-width` 治不了的下限）

**证据**
- `@media (min-width:1025px)` 一开，侧栏 290 + TOC 250 = 540px 固定占用：正文 693px（1024）**骤降到 434px（1025）**，即 **80.3ch → 50.3ch（-37%）**。
- 逐点：1025 → 50.3ch / 1100 → 59.0 / 1159 → 63.8 / 1200 → 70.6 / 1280 → 79.9。
- 关键：**`max-width` 只能封顶，不能兜底**。在此区间加任何 `max-width` 都**无效果**（实测 `p7`/`p8`：1025 下 `max-width:560/605/640` 全部测得 prose=434，一字未变）。

**改成什么**（二选一，按「宁可少一个导航」优先）
```css
/* 方案一：右栏 TOC 断点上移到 1200（推荐） */
@media (min-width:1025px) and (max-width:1199px){
  .layout.has-toc{ grid-template-columns:290px minmax(0,1fr) }
  .toc-side{ display:none }
  .side-toc{ display:block }      /* 回落到抽屉里的本页目录 */
}
```
实测：1100 下 **59.0 → 88.0ch**（TOC 隐藏后 759px），1199 下 **63.8 → 99.5ch**；**叠加 40rem 封顶后统一收敛到 74.2ch**（见 §4.4）。代价：1025–1199 失去常驻右栏（回落到抽屉里的 `.side-toc`）。

```css
/* 方案二：收窄两栏，保 TOC */
@media (min-width:1025px) and (max-width:1199px){
  .layout.has-toc{ grid-template-columns:256px minmax(0,1fr) 200px }
}
```
实测：1025 下 **50.3 → 60.0ch**（434 → 518px）；1100 下 **59.0 → 68.7ch**。代价：侧栏与 TOC 各变窄，长标题更多省略号。

**为什么**：`max-width` 解决「太宽」，但 1025–1199 是「太窄」。二者必须分开处理，否则会出现「在 1440 加了限宽，在 1100 反而更糟」的错觉。建议**方案一**，因为 50ch 已低于 Bringhurst 下限 45 的邻域，而右栏目录在窄屏本就难用。

### H2-2　移动端 H1 掉到首屏外 1.6–2.4 屏（y=1317 / 1345）

**证据**
- `.toc-side{order:1}` + `.content{order:2}`（`site.css:101-102`）；`<details class="toc-fold" open>` 默认展开，24 条 × 44px = **1173px**。
- 390×844：H1 y=**1317**（视口 844）；320×568：H1 y=**1345**（视口 568）。
- 首段正文 y=1562 / 1597。

**改成什么**
```css
@media (max-width:1024px){
  .content{ order:1 }
  .toc-side{ order:2; margin:1.2rem 0 0 }
}
```
并从渲染层去掉 `.toc-fold` 的 `open` 属性（默认折叠）。

**为什么**：实测仅调 order（目录仍在但排到正文后），H1 从 **1317 → 129**（390）、**1345 → 156**（320），**进入首屏**。这是全站**单条改动收益最大**的修复（读者少滚 1.5–2 屏）。注意：44px 触控行高是移动端硬要求，**不应缩小**，只应换位置。

### H2-3　light 主题下 8 个代码 token 不达 AA（3.87 / 3.97）

**证据**：`#3f8f4f`（string/regexp/addition）on `#fbfbfd` = **3.87:1**；`#b06f00`（built_in/builtin_name/meta/tag）= **3.97:1**。这是**不依赖主题切换**的缺陷，所有 light 用户可见。

**改成什么**
```css
.hljs-string,.hljs-regexp,.hljs-addition{ color:#2f7239 }   /* 3.87 → 5.66 */
.hljs-built_in,.hljs-builtin-name,.hljs-meta,.hljs-tag{ color:#8a5600 } /* 3.97 → 5.96 */
```
折中值：`#33753f`(5.41) / `#965d00`(5.26)，若嫌过深。

**为什么**：WCAG 1.4.3。选 `#2f7239`/`#8a5600` 是因为它们在**保持原有色相**（绿 / 琥珀）的前提下过线，不破坏高亮语义。

### H3-1　字号阶梯末两级塌陷（h4≈正文、h5=h6<正文）

**证据**：h4 16.32px（正文 16px，差 **0.32px**）；h5=h6=**15.2px（0.95× 正文）**，且 `--fg-muted`；h4/h5 = 1.074（< 1.15 可辨门槛）；h5/h6 = **1.000**（完全同规格）。
**改成什么**：见 §2 维度 2 的 1.25 音阶建议（h1 2rem / h2 1.5 / h3 1.25 / h4 1.125 / h5 1 / h6 .9375）。
**为什么**：六级标题体系实际只有五级可用，且最小两级比正文更弱——语义倒挂。

### H3-2　跨页同语义元素四套规格

**证据**：正文 16.8px（落地页）vs 16px（其余）；H1 32 / 29.6 / 28.8 三套；H2 21.6 vs 22.4；正文列宽 949 vs 849。
**改成什么**：统一 16px/1.7；H1 2rem；H2 1.5rem；列宽统一 40rem。
**为什么**：一致性是最低成本的「专业感」来源，4 套值没有任何设计理由。

### H3-3　图片留白 12px 低于代码块 16px

**证据**：`<img>` 嵌在 `<p>` 内，继承 `p` 的 12px 上下边距；而 `.code-block`/`.table-wrap`/`.alert` 均为 16px。`confirmation-dialog.webp` 渲染 849px 宽，上下仅 12px。
**改成什么**：`img.content-img{ display:block; margin:24px auto }`。
**为什么**：图片是高注意力块，应比代码块有更大的呼吸空间（视觉权重越高，留白应越大）。

### H3-4　字重 650 非标准档位

**证据**：`.alert-title{font-weight:650}`；`Noto Sans SC` / `Microsoft YaHei` 无 650 字面 → 浏览器合成加粗。
**改成什么**：650 → 600。
**为什么**：合成加粗在中文上会让笔画粘连（尤其中小字号）。

### H3-5　表格数字未显式 `tabular-nums`

**证据**：`1` 与 `8` 均 7.76px（该字体天然等宽），但 `font-variant-numeric: normal`。仅 `.side-count`/`.stat b` 显式声明。
**改成什么**：`.table-wrap table{ font-variant-numeric:tabular-nums }`。
**为什么**：当前是「字体巧合」而非「声明意图」，换字体栈即破。

### H3-6　输入框边框 1.26:1（WCAG 1.4.11 不可豁免）

**证据**：`.side-filter`/`.hero-search #hero-search`/`.filter-bar input` 用 `--border #e2e5ea` on 白 = **1.26:1**（需 3:1）。
**改成什么**：输入框专用 `#8b919c`（3.17:1）；深色 `#5b6474`（3.04:1）。装饰性分隔线保持 `--border`。
**为什么**：可聚焦控件是 UI 组件，1.4.11 直接适用；但全站边框都提到 3:1 会让页面「表格化」，故只改输入框。

## 4. 可直接粘贴的 CSS 方案

### 4.1 方案 A（推荐）：只封行文块 + TOC 断点上移 + mobile 目录后置

> 实测数据见 §4.3。**不依赖任何未被验证的假设**，每条都在 `p14`/`p20` 验证过。

```css
/* ============ 1. 行宽（measure）：只封行文块，不碰代码/表格/图片 ============ */
@media (min-width:768px){
  .article > :is(p,ul,ol,blockquote,dl),
  .article li > :is(p,ul,ol){
    max-width: 40rem;          /* 640px = 74.2ch = 40 全角 */
  }
}

/* ============ 2. 1025–1199 的「下限」修复：TOC 断点上移到 1200 ============ */
@media (min-width:1025px) and (max-width:1199px){

  .toc-side{ display: none }

/* ============ 3. 移动端：正文在前、目录在后，且默认折叠 ============ */
@media (max-width:1024px){
```

### 4.2 方案 B（保底）：整列封顶 + 居中

若不想动选择器列表，可只封 `.article` 整列：

```css
@media (min-width:768px){
  .article{ max-width:40rem; margin-inline:auto }
}
```

**权衡**：正文同样是 74.2ch，但**代码块与表格也被压到 640px**，实测代码块横向滚动从 **5/13 升到 7/13**（`p20`），且右空仍有 380px（1440）。**方案 B 更省事但体验更差**，仅在无法细调选择器时采用。

### 4.3 与现有样式的冲突点（必读）

| 冲突 | 说明 | 处理 |
|---|---|---|
| `.content{max-width:1000px}`（`site.css:505`、`544`） | 这是**容器封顶**，不是 measure。方案 A 在其内部再封 40rem，两者**不冲突**（1000px 容器内放 640px 行文块，右空 308px）。**不要**为了「达标」把 1000px 改成 44rem——44rem=704px=**81.6ch 仍超 75**，且会同时压窄代码块。 | 保留 1000px；行宽由方案 A 单独负责 |
| `.hero p{max-width:76ch}`（`site.css:300`） | 落地页已有 76ch 约束（实测渲染 688px ≈ 79.7ch，因 `ch` 按该元素字体算）。 | 保留；与 40rem 并存时取小值，落地页正文会变 640px，**符合预期** |
| `.layout.has-toc{grid-template-columns:290px minmax(0,1fr) 250px}`（`site.css:533`） | 方案 A 的第 2 条在 1025–1199 覆盖它。**特异性相同（都是 0,2,0）但媒体查询更窄**，需放在**其后**才能生效。 | 追加到 `site.css` 末尾（断点层之后） |
| `.toc-side{order:1}` / `.content{order:2}`（`site.css:101-102`） | 方案 A 第 3 条在 `max-width:1024px` 反转。原规则无媒体查询包裹，**新规则必须带 `@media`** 才能只影响移动端（否则桌面 `order:0` 会被覆盖）。 | 已按此写；且 `>=1025px` 的 `site.css:539` 有 `.content{order:0}` 兜底 |
| `.article{overflow-wrap:anywhere}`（`site.css:194`） | 实测未造成正文词中断（1440/390 均 0 次），**不要删**——它是长 URL/长 token 的防溢出安全网。 | 保留 |
