## 5. 值得夸的（≥3 条）

### 5.1　正文基准 16px / 1.7 全站统一，且中文行高选对了

`body{font-size:16px;line-height:1.7}`（`site.css:43`）——16px 是中文正文的可靠基准，**1.7 的行高在中文长读场景是正确选择**（中文 1.7–1.9，西文 1.4–1.6，取 1.7 兼顾了两者）。

更值得夸的是**一致性**：`/paper/`、`/paper/dev/dialogs/`、`/velocity/tuning/`、`world-configuration` 的正文全部是 16px/27.2px，**四个页面零漂移**（`p15` 实测字号分布 `{16: 296}`、`{16: 49}` 等）。在 141 页的静态站里做到这点，说明生成管线是收敛的。唯一的例外是落地页的 `.hero-tag` 16.8px，属可修的小瑕疵。

### 5.2　`measure.json` 的量尺设计（`ch` / `chText` / `cjk` 三口径）是专业级的

多数站点的「行宽」是用「容器宽 ÷ 字号 × 0.5」估算的拉丁近似——那个公式对中文完全失真。本站的量尺做了三件对的事：

1. 用 `Range.getClientRects()` 量**真实行盒**，而不是用容器宽推算；
2. 用 canvas 的 `measureText('0')` 取**该字体真实的 zero advance**（8.63px），而不是假设 0.5em；
3. 同时给出 `ch`（容器容量）、`chText`（实际最长行）、`cjk`（全角字）三个口径，并明确 `ch` 是主口径。

这让「98.4ch」这个数字可以被任何人用「849 ÷ 8.63」复算出来。**度量透明是锐评可信的前提**，这一点做得比大多数同类报告好。

### 5.3　`headingScale` 抓出了真实的 h4≈正文、h5=h6<正文（而非旧口径的「三档字号」）

量尺没有停在「h1 到 h6 各多大」，而是同时输出 `counts`（h2/h3/h4 实际出现次数）。这个设计直接揭穿了本站两个结构性问题：

- `world-configuration` 页 **h2/h3/h4 计数为 0**（36260 字符、77 屏无标题）——如果只看「h2 的 font-size」，会得出「h2 是 22.4px，没问题」的错误结论；
- `dialogs` 页 h2/h3/h4 = 8/9/7，说明标题体系在**其他页面是工作的**，问题被精确定位到特定页面而非全站。

我用 `tools/critique-typo-counts.js` 直接数构建产物的 `<h2` 标签做了交叉验证，两者一致。随后用 `p25` 把范围扩到**全站 144 个 URL**，才发现这不是单页问题而是「键值配置参考」整个内容族的系统缺失（6 页、90299 字符，见 H1-3）——**量尺给出的 `counts` 字段是这条线索的起点**。该字段可信。

### 5.4　暗色令牌的对比度整体健康（dark 下 29/29 token 全过 AA）

`html[data-theme="dark"]` 那套色板不是「把浅色反相」，而是**重新调过亮度**的：

| token | light | dark | dark 相对 light |
|---|---|---|---|
| keyword | 5.92 | 8.96 | +51% |
| string | **3.87** | 11.35 | **+193%** |
| number | 4.71 | 9.39 | +99% |
| comment | 4.68 | 5.76 | +23% |

dark 下**最低 5.76:1**（comment），全部 29 个 token 通过 AA。这是有意识的设计——尤其 string 从 3.87 修到 11.35，说明作者知道绿在浅底上不够、在深底上要提亮。**问题只在于「auto 路径没继承这套色板」**（见 H1-1），一旦补上就完整了。

### 5.5　代码排版的核心参数选得准

- 代码字号 **13.6px（0.85rem）**：文档站代码字号的行业惯例是 0.85–0.9× 正文，13.6px @ 16px 正好落在下沿，既保证 80 列可读又不抢正文风头；
- 代码行高 **1.55**：代码需要比正文紧（1.5–1.6），1.55 是标准值；
- `tab-size: 2`：与 Java / YAML / JSON 生态一致（这两类内容占本站代码块绝大多数）；
- 真正的等宽字体栈 `ui-monospace, SFMono-Regular, "JetBrains Mono", …`，实测 `i` 与 `W` 同宽（7.97px），**不是伪等宽**；
- `pre` 的横向滚动被约束在 `.code-scroll` 单一容器内（`site.css:226-230`），且键盘可聚焦、有 `focus-visible` 环——**长代码不会撑破文档宽度**（实测 1440 下 `document.scrollWidth == clientWidth`）。

这五点合起来是一套**教科书级的代码块排版**。

### 5.6　`overflow-wrap` 的分层策略是对的（且被误判了）

`site.css:56` 与 `194`：
```css
:not(pre)>code{ overflow-wrap:anywhere }   /* 行内代码允许断 */
.article{ overflow-wrap:anywhere }          /* 正文兜底 */
```
初看像「到处乱断」，但实测（`p4`）证明它**在有空间时根本不触发**：1440 与 390 下正文词中断 **0 次**，关闭该属性后文档宽度不变（1440→1440）。它只在**极端窄容器**里救场——这是「安全网」而非「常规断行」。

真正的 `Administrat/ion` 是**侧栏**的 `text-overflow:ellipsis` 造成的（`.grp-name{white-space:nowrap;overflow:hidden}`，容器 84px / 内容 91px），与 `overflow-wrap` 无关。**这个属性的设计意图是正确的，不该被当作缺陷改掉。**

## 6. 不确定性（哪些是审美偏好，哪些是硬结论）

### 6.1 硬结论（有规范条文 + 本机可复算数值，不依赖偏好）

| 结论 | 依据 | 可复算性 |
|---|---|---|
| auto 路径 hljs 30/30 不达 AA（keyword 2.85:1） | WCAG 1.4.3 明文 4.5:1 | `2.85 = ratio(#a626a4, #171a1f)`，任何人可算 |
| light 下 8 个 token 3.87 / 3.97 不达 AA | 同上 | 同上 |
| 输入框边框 1.26:1 不达 3:1 | WCAG 1.4.11 明文 3:1 | `ratio(#e2e5ea, #ffffff) = 1.26` |
| `world-configuration` 有 0 个 h2/h3/h4 | DOM `querySelectorAll` + HTML 标签计数**双验** | 打开页面搜索 `<h2` 即可 |
| 1440 下正文行宽 98.4ch | `849px ÷ 8.63px` | 可用 `getComputedStyle` + canvas 复算 |
| 1025 下正文 50.3ch（断崖） | `434px ÷ 8.63px` | 拖动窗口到 1025px 即可复现 |
| 移动端 H1 在 y=1317（首屏外） | 元素 `getBoundingClientRect` | 直接量 |

### 6.2 审美偏好（我给的是「有理由的选择」，不是「唯一正确答案」）

| 项 | 我的取值 | 为什么这是偏好 | 若你有不同取向 |
|---|---|---|---|
| **行宽 40rem / 74.2ch** | Bringhurst 上限内侧 | 74.2 与 66ch（更保守）都可辩护；中文语境下有人主张 35 全角（560px） | 若追求「极致舒适」→ **36rem(66.8ch)**；若不想动太多 → **44rem(81.6ch)**，但需承认仍超 Bringhurst |
| **1.25 音阶** | h1 32 / h2 24 / h3 20 / h4 18 | 1.25 与 1.333 都是经典音阶，选谁取决于「想不想要更强的层级对比」 | 若要更戏剧化 → **1.333**（h1 32 / h2 24 / h3 18），但 h3/h4 会拉开过大 |
| **垂直节奏改 8px 网格** | p 16、块级 24 | 「严格网格」是 Bringhurst 派的执念，Web 上很多优秀站点不用网格 | 若不想改 → 保留 12/16，只修「图片 12 < 代码 16」这一处**明确不合理**的倒挂 |
| **1025–1199 隐藏 TOC** | 方案一 | 「宁可少导航也要够宽」vs「宁可窄也要有导航」是**产品取向**，不是排版对错 | 若认为 TOC 不可少 → 方案二（收窄到 256/200，1025 下 60ch） |
| **代码字体 13.6px** | 0.85rem | 13.6 与 14.4（0.9rem）都合规 | 若觉得偏小 → **0.9rem = 14.4px**，仍远优于「与正文同号」 |
| **h5/h6 用 1rem/.9375rem** | 不低于正文 | 「h6 不小于正文」是层级逻辑要求，但**具体到多少**是偏好 | 也可 h5 1.0625rem / h6 1rem |

### 6.3 我**无法**确认的（能力边界，明确声明）

1. **VitePress / Starlight / Docusaurus 的官方默认列宽**：本机 DNS 受限（`raw.githubusercontent.com`、`github.com` 均解析到非公网 IP），**未能联网复核**。因此报告**没有**把「Starlight 45rem」「VitePress 688px」之类数字写进基准——前一实例的骨架里有这些数字，本版**主动剔除**，改为只用 Bringhurst / Butterick / WCAG / 中文行高惯例。
2. **`overflow-wrap: anywhere` 在 Safari / Firefox 下的断行差异**：本轮只用 Chromium 测量。`anywhere` 与 `break-word` 的差异（前者影响 `min-content` 尺寸计算）在 Gecko/WebKit 上可能表现不同，未验证。
3. **真实设备的中文字体落点**：测量环境是 Windows（`Microsoft YaHei` 命中）。macOS（`PingFang SC`）与 Android（`Noto Sans SC`）下 `信` 的实际宽度、以及 1.7 行高的观感会有差异，未跨平台验证。
4. **`auto` 模式下浏览器「跟随系统」的具体实现**：我用 `colorScheme: 'dark'` + `data-theme="auto"` 模拟，与真实 OS 切换可能有细微差别（如 `prefers-color-scheme` 的变更事件时序）。
5. **`world-configuration` 的标题缺失是「构建 bug」还是「上游源文件本身无标题」**：我只验证了产物无 h2，**没有**回溯上游 `docs.papermc.io` 原始 Markdown 是否本来就没有 h2。若上游本就无标题，则修复点在「内容加工」而非「构建映射」。**这一点需要看 `build-site.js` 与源文件才能定论。**
6. **色觉障碍视角**：本轮只算 WCAG 对比度，**未做** protanopia/deuteranopia 模拟。hljs 靠「紫/绿/橙/蓝」区分 token，对红绿色盲可能有辨识困难（这是所有基于色相的高亮的通病，非本站特有）。

### 6.4 一处需要澄清的「假缺陷」

前一实例与红队都提到「`overflow-wrap:anywhere` 把 `Administration` 切成 `Administrat/ion`」。**本轮证伪**（`p4`）：

- `.grp-name` 的 `overflow-wrap` 实际是 **`normal`**，`word-break: normal`，`white-space: nowrap`，`overflow: hidden`，`text-overflow: ellipsis`；
- 容器 `clientWidth: 84px`，内容 `scrollWidth: 91px` → **溢出后被省略号截断**，截断点在 `Administrat|ion` 处；
- 390px 下容器 91px，**不截断**（整词显示）；320px 下容器 75px，截断成 `Administrat|ion`。

所以这是**容器的溢出裁剪**，与 `overflow-wrap` 无关。真正的修法是给 `.grp-name` 更宽的容器，或允许折行（但那会让侧栏每行变两行高）。**`overflow-wrap:anywhere` 不应为此负责，也不应被删除。**

## 7. 修复优先级（若只做三件事）

| 顺序 | 改动 | 收益 | 风险 | 工作量 |
|---|---|---|---|---|
| 1 | **auto 路径补 hljs token**（§4.1 第 4 段） | 默认路径 30 个 token 从全失败 → 全通过 | **零**（dark 数值不变，已验证） | 复制粘贴 10 行 |
| 2 | **移动端目录后置**（§4.1 第 3 段） | H1 从 1345 → 156，进入首屏 | 低（仅 `order`，触控尺寸不变） | 3 行 |
| 3 | **行宽 40rem 封行文块 + TOC 断点上移**（§4.1 第 1–2 段） | 1440 从 98.4 → 74.2ch；1025 从 50.3 → 74.2ch | 低（代码块滚动 5/13 不变，已验证） | 8 行 |

第 1 条是**纯 bug 修复**（一行选择器写错），第 2 条是**收益/成本比最高**的一条，第 3 条才是「排版品味」层面的改动。三件事都不需要改 HTML 结构。

**必须由构建层修、CSS 修不了的（优先级同 H1）**：
4. **`cli-arguments` 的 31 个 `<h5>` 提为 `<h3>`**，以及**5 个配置参考页补 `<h2>`**（H1-3）。这涉及 90299 字符、全站 12.5% 的正文，但改动点在 `build-site.js`，不在 `assets/site.css`。

**关于字号阶梯的补充实测**：我原先在草稿里写过「h5/h6 全站用量为 0，修了也没人用」——**这是错的，已更正**。全站 144 页实测（`p22`/`p24`/`p25`）：

| 标签 | 全站次数 | 涉及文件 |
|---|---|---|
| `<h5>` | **46** | 4 个页面（`cli-arguments` 31、`pdc` 10、`using-databases` 4、`scheduler` 1） |
| `<h6>` | **0** | 0 个页面 |

所以：
- **h5 是真实在用的**（46 处），且渲染为 **15.2px / #5c6470 / 5.98:1**，正文为 **16px / #1c1f26 / 16.49:1**（`p23` 逐页验证）——这 46 处「五级标题」视觉上**比正文更弱**，是实打实的倒挂。
- **h6 确实零使用**，给 h6 定值属于「为完整性而设」，可不动。

修正后的判断：字号阶梯**真正待修的是 h5 与 h4**，而不是整条音阶。若只改两行：

```css
.article h4{ font-size:1.125rem; line-height:1.45; color:var(--fg) }                  /* 16.32 → 18 */
.article h5{ font-size:1rem;     line-height:1.5;  font-weight:700; color:var(--fg) } /* 15.2 → 16, 去 muted */
```

**不建议优先做的**：全量音阶重排（§4.1 第 6 段）。它影响 144 页所有标题，收益是「层级更统一」，但 h1–h3 尚可用。**先修行宽、h5/h4、以及缺标题的 6 个配置页。**
