## 2. 12 维度判定表

判定用四档：**优**（可直接作为同类站点的参考）／**良**（有可改进项但不伤阅读）／**疑**（有明确缺陷，影响阅读效率）／**劣**（达标线以下，必须修）。

### §1 行宽（measure）

**测量值**：1440 下 `capCh` = **98.4ch（有 TOC）/ 110ch（无 TOC）**；`p90` 74.9–97.2ch；`max` 98.4–107.6ch。全站仅 `.hero p{max-width:76ch}`（`site.css:300`）一处有行宽约束，且只作用于落地页首屏那两段。`.article p` **无任何 max-width**。

**基准**：Bringhurst 45–75 字符/行；Butterick 45–90。中文语境下「全角字/行」经验区间 **30–40**（对应 45–60 拉丁字符的信息密度），最宽不宜超 **45 全角**。

**判定：劣。** 超上限 31–47%（对 Bringhurst），且是**唯一直接决定长读效率的维度**。真实代价：`/paper/reference/world-configuration/` 单行 919px，读者从行尾回到行首需水平移动约 640px；`/paper/dev/dialogs/` 正文 849px / 53 全角字，已超中文舒适上限 45 约 18%。

**具体数值建议**：见 §4 完整方案。核心是 **40rem（640px）= 74.2ch / 40 全角**，落在 Bringhurst 上限 75 内侧且等于中文经验上沿 40。

---

### §2 字号阶梯（type scale）

**测量值**：见 §1.3 全表。比例 1.286 → 1.207 → 1.137 → **1.074** → **1.000**；`h4/正文 = 1.02`；`h5=h6=0.95×正文`。

**基准**：常用音阶为 1.25（大三度）、1.333（纯四度）、1.2（小三度）。要求：① 相邻级比 ≥ 约 1.15 才可辨；② **末级不得小于或等于正文**（正文是「基准层」，标题任何一级都应更醒目）。

**判定：劣。** 两处硬缺陷：
1. **跳级衰减**：1.286/1.207/1.137 尚在可辨范围，但 1.074 已低于 1.15 门槛，`h4`（16.32px）与正文（16px）仅差 **0.32px**——实际靠 `color:var(--fg)` 与字重 700 撑层级，字号本身不承担区分。
2. **末两级塌陷**：`h5`、`h6` 均为 **15.2px，比正文 16px 更小**，且 `color:var(--fg-muted)`（更灰）。语义上「六级标题」却比正文更弱，是**层级倒挂**。
3. 附带问题：**h6 与 h5 完全同规格**（size/weight/line-height/margin 全等），六级体系实际只有五级。

**具体数值建议**：改用 **1.25 音阶 + 正文锚定 1rem**：
`h1 2rem(32) / h2 1.5rem(24) / h3 1.25rem(20) / h4 1.125rem(18) / h5 1rem(16, 700, --fg) / h6 .9375rem(15, 700, --fg-muted)`。
关键约束：**h4 ≥ 18px（≥1.125× 正文）**；**h5 不小于正文**（可同号但必须换字重+颜色双通道）；**h6 必须与 h5 有可见差异**。

### §3 行高（line-height）

**测量值**：正文 **27.2px / 1.7**；h1 1.25；h2–h4 1.35；行内/块级代码 1.55；表格 1.7；列表 1.7。

**基准**：中文正文 1.7–1.9；西文 1.4–1.6。标题可紧（1.2–1.35），但**中文标题换行时 1.25 偏挤**（汉字上下留白本就少）。

**判定：良。** 正文 1.7 是**正确选择**（16px 中文长读的合理值，且与「行宽过宽」形成部分补偿）。扣分项在标题：`h1` 1.25 在中文标题折行时字面几乎相碰；`h2–h4` 统一 1.35 而未随字号递减调整（22.4px 与 16.32px 用同一比值，大字实际更挤）。

**具体数值建议**：正文保持 **1.7**（不动）；`h1` 提到 **1.35**（28.8→32px 时行高 43.2）；`h2/h3` 用 **1.4**；`h4` 用 **1.45**。理由：字号越小越需要更大行高比来维持视觉密度一致。

**附带（WCAG 1.4.12 文本间距）**：全文行高 1.7 已远超 1.5 下限，段落间距 12px > 2×字号？——**未达**。1.4.12 要求段间距 ≥ 2em（32px），现为 12px。此项对**默认样式**不强制（1.4.12 约束的是「用户覆盖后不得丢内容」），故仅记录不判失败。

### §4 垂直节奏（vertical rhythm）

**测量值**：直接子块 **12 种不同 margin 组合**；`p` 上下 12/12；`ul` 9.6/9.6；`li` 4/4；`pre`/`table`/`alert`/`figure`/`details` 统一 16/16；`h2` 40.32/13.44、`h3` 33.41/11.14、`h4` 29.38/9.79。

**基准**：单一基线网格（如 8px 或其半数 4px）能让整页纵向节奏稳定；标题上下边距应成**固定比例**（如 3:1），且随级别递减。

**判定：疑。** 三个具体问题：
1. **非网格化**：27.2（行高）、12、9.6、16、40.32、13.44、11.14、9.79 混用，无公因数。27.2 本身不是 4 的倍数（6.8×4），导致任何「按行对齐」的间距都无法整除。
2. **标题比例不统一**：h2 上/下 = **3.0**，h3 = **3.0**，h4 = **3.0**（这部分是好的，因为都源自 `1.8em/0.6em`）。但 `.hero h1`（margin `.2rem 0 .4rem` = 3.2/6.4）与 `.article h1`（1.6/5.6）不同，同语义两套值。
3. **图片留白被低估**：`<img>` 包在 `<p>` 里，因此只拿到 `p` 的 12px 上下边距，而代码块/表格/提示框都是 16px。图片作为「高注意力块」反而比代码块更贴文字。实测 `confirmation-dialog.webp` 渲染 849×? 宽，上下仅 12px。

**具体数值建议**：把纵向单位改为 **8px 网格**：`p` 上下 **16/16**（= 0.5 行）、`ul/ol` **16/16**、`li` **4/4** 保留、块级组件（pre/table/alert/figure/details）**24/24**、`h2` **48/16**、`h3` **40/16**、`h4` **32/12**。并给 `img.content-img` 显式 **24/24**（脱离 `p` 的 12px 继承）。代价：页面会变长 3–5%（实测 `p` 由 12→16 会让 dialogs 页 13737 → 约 14300，见 §4 验证数据），这是可接受的交换。

### §5 字重与强调（weight & emphasis）

**测量值**：`.article` 内字重分布 **400: 625 个元素 / 600: 9 / 650: 2 / 700: 29**。强调手段：`<strong>` 2 个、`<em>` 0 个、行内 `<code>` 75 个、链接 70 个、`<kbd>` 3 个（在顶栏而非正文）、`<mark>` 0。

**基准**：字重档位宜 **2–3 档**（regular / semibold / bold）；强调手段宜 ≤ 3 种并用，且**每种有唯一语义**。

**判定：良（但有一处隐性滥用）。**
- 好的部分：字重只有 400/600/700 三档（650 是 `.alert-title`，属第四档的零头，可并入 600 或 700）；`strong` 仅 2 处、`em` 为 0，**没有滥用加粗/斜体**。
- 问题所在：**行内 `<code>` 承担了「技术名词标记」的职责**（75 处 vs strong 2 处）。这在文档站是合理惯例，但当前行内代码的视觉权重偏高：`background:var(--bg-elev)` + `border:1px solid var(--border)` + `padding:.05em .3em` + `border-radius:5px`，在 1440 下一段文字里出现 5–8 个「小方框」，**形成视觉噪点**（截图 `1440x900/content-callout-code.fold.png` 可见）。对比度 14.87:1 也远高于正文 16.49:1 所需，过于抢眼。
- 另一处：`.alert-title` 用 `font-weight:650`（非标准档位，且 `Noto Sans SC`/`Microsoft YaHei` 无 650 字面，浏览器合成加粗，笔画会发糊）。

**具体数值建议**：字重收敛为 **400 / 600 / 700** 三档，把 650 改 600。行内代码**去掉边框**、底色从 `--bg-elev`（`#f2f3f7`）改为更淡的 `color-mix(in srgb,var(--accent) 8%,var(--bg))`，或保留边框但把 `padding` 从 `.3em` 降到 `.2em`、`border-radius` 5→4px——目的是**降低单点的框感**，让它读起来像「字」而不是「控件」。

### §6 对比度（contrast）

**测量值**：见 §1.6 全表。要点：

- **正文/次要/链接/行内代码/徽章：三路径全 PASS**，最低值 4.83（badge-danger on white），余量健康。这一块做得**很好**。
- **`auto` + 系统深色：代码高亮 30/30 全失败**（2.85–4.36）。根因是结构性的：

  ```css
  /* site.css:29-40：auto 只搬了 :root 令牌 */
  @media (prefers-color-scheme: dark){ html[data-theme="auto"]{ --bg:#14161a; ... } }
  /* site.css:436-442：dark 的 hljs 规则只写了 [data-theme="dark"] */
  html[data-theme="dark"] .hljs-keyword{ color:#d2a8ff }
  ```

  `data-theme="auto"` **永远不匹配** `[data-theme="dark"]`，所以 auto 模式下：**底色变深了，token 颜色还是浅色板那套**。keyword `#a626a4` on `#171a1f` = **2.85:1**（红队与前一实例都提到这个数字，本轮独立复现并确认）。

- **light 下 8 个 token 不达 AA**：string 组 `#3f8f4f` = 3.87；built_in/meta/tag 组 `#b06f00` = 3.97。这是**独立于主题切换的缺陷**，任何用户都会看到。
- **非文本 3:1**：所有装饰边框 1.19–1.76，全部不达。装饰性分隔线（H2 下边框、表格线）可豁免；但**输入框边框**（`.side-filter`、`.hero-search #hero-search`、`.filter-bar input`）是 UI 组件，**不可豁免**。

**基准**：WCAG 2.2 1.4.3（4.5:1 / 大字 3:1）、1.4.11（3:1）。

**判定：疑（分区判定）**——「正文类对比度：优」「代码高亮 auto 路径：劣」「UI 边框：疑」。

**具体数值建议**：

1. **auto 路径**（最高优先级）：把 `site.css:436-442` 的 7 条 `html[data-theme="dark"] .hljs-*` 规则**复制一份给 `auto`**，包进 `@media (prefers-color-scheme: dark)`。已实测：补丁后 auto 从 **7/7 失败 → 0/7 失败**（keyword 2.85 → **8.96**），dark 路径数值**完全不变**（见 §4 验证）。
2. **light 的 8 个 token**：`--hljs-string: #3f8f4f → #2f7239`（3.87 → **5.66**）；`--hljs-builtin: #b06f00 → #8a5600`（3.97 → **5.96**）。或折中取 `#33753f`(5.41) / `#965d00`(5.26)。
3. **UI 边框**：`--border-strong` 用于**输入框/可聚焦控件**时改为 `#8b919c`（白底 **3.17:1**）/ 深色 `#5b6474`（深底 **3.04:1**）；装饰性分隔线保留 `--border` 不动（避免整页变「表格化」）。

### §7 等宽与数字（monospace & numerals）

**测量值**：字体栈 6 段回退，实测**真等宽**；`pre` 盒子 16px 但内部 `code` **13.6px（0.85rem）**；表格数字天然等宽（`1`=`8`=7.76px）但 `font-variant-numeric: normal`；仅侧栏计数/统计块显式 `tabular-nums`。

**基准**：代码字号宜 **0.85–0.9× 正文**（13.6–14.4px @ 16px 正文），行高 1.5–1.6；**技术文档里的代码不应小于 12px**；表格数字列应显式 `tabular-nums`。

**判定：良。**
- 好的部分：13.6px / 1.55 行高是**教科书级取值**（既保证 80 列代码可读，又不至于比正文抢眼）；真等宽已由 `ui-monospace` 保证；`tab-size:2` 与 Java/YAML 生态一致。
- 待改：① `pre` 的 `font-size:16px` 与内部 `code` 的 `.85rem` **两套值**，`getComputedStyle(pre).fontSize` 报 16 会误导后续维护者（也是一个度量陷阱：`measure.json` 的 `codeBlock.fontSize` 就报了 16）；② 表格数字**依赖字体巧合**而非显式声明，换字体栈（如换到不含等宽数字的字体）就会错位；③ 代码块**无行号**（`hasLineNumbers:false`），13 个代码块里有长 YAML，引用行号困难。

**具体数值建议**：`pre` 字号直接写 **`0.85rem`**（与内部 `code` 统一，消除双值）；`.table-wrap td.num, .table-wrap td:has(...)` 或干脆 `.table-wrap table{font-variant-numeric:tabular-nums}`；代码块行号属增强项，建议对 **>15 行**的块启用（当前 13 块中 YAML 有 30+ 行）。

### §8 首屏阅读引导（above-the-fold reading entry）

**测量值**（`/paper/dev/dialogs/`）：

| 视口 | 顶栏 | 面包屑 y | **H1 y** | 描述 y | chips y | 首段正文 y | 视口高 |
|---|---|---|---|---|---|---|---|
| 1440×900 | 52 | 74 | **109** | 156 | 194 | 238 | 900 |
| 390×844 | 56 | 1261 | **1317** | 1365 | 1402 | 1562 | 844 |
| 320×568 | 56 | 1261 | **1345** | 1392 | 1455 | 1597 | 568 |

- 桌面：H1 在 y=109，**首屏内**（好）。
- 移动：H1 在 **y=1317 / 1345**，而视口只有 844 / 568 —— **H1 在首屏之外 1.6–2.4 屏**。原因是 `.toc-side{order:1}` + `.content{order:2}`（`site.css:101-102`），24 条目录 × 44px = **1173px** 全部堆在正文之前，且 `<details open>` 默认展开。
- chips 位置：DOM 顺序为 `h1 → .page-desc → .page-meta(4 chips) → 正文`，**chips 在 H1 之后**，未破坏「从标题开始读」。但 4 个 chip 占 32px（桌面）/ 148px（390，换行成 4 行）。chip 内容含「源结构第 92 篇 / 共 103 篇」这类**构建期元数据**，对读者价值低却占了正文前的黄金位置。

**基准**：H1 应落在首屏内（移动端首屏 ≤ 1 屏）；正文首段宜在首屏可见 3–5 行。

**判定：劣（仅移动端）。** 桌面端 **优**。

**具体数值建议**：移动端把 `.content{order:1}`、`.toc-side{order:2}`（目录移到正文之后），并让 `.toc-fold` **默认不 `open`**。已实测：仅调 order 后 H1 从 **y=1317 → y=129**（390×844）、**1345 → 156**（320×568），**进入首屏**。chips 建议把「源结构第 N 篇 / 共 M 篇」降级为页脚信息。

### §9 长页面疲劳（long-page fatigue）

**测量值**：

| 页面 | 字符数 | 页高(1440) | 页高(320) | h2/h3/h4 | 标题间隔 |
|---|---|---|---|---|---|
| `/paper/dev/dialogs/` | 19066 | 13737 | 20090 | 8/9/7 | 794 字符 |
| `/paper/reference/world-configuration/` | **36260** | **16180** | **43733** | **0/0/0** | **无标题** |

- 320×568 下 `world-configuration` 高 **43733px = 77 屏**（每屏 568px），且**全程没有一个 h2/h3/h4**。
- 该页 96% 的内容是嵌套列表：`li` 共 **273 个**，嵌套深度分布 `{1:18, 2:92, 3:94, 4:48, 5:17, 6:4}`，最深 **6 层**。
- 缩进侵蚀：每层 `ul{padding-left:1.5em}` = **24px**，6 层累计 **144px**。在 320px 视口下，正文列 288px 减去 144px 只剩 **144px = 17.6ch / 9 全角字**——这解释了 §1.1 中 `world-configuration` 在 320 下 `p90` 仅 24.2ch。
- 卷动条（scrollbar）在 43733px 高度下已失去导航价值。

**基准**：长文档应每 **500–1500 字**有一个可扫描标题；嵌套列表深度 ≤ 3–4 层。

**判定：劣。** 「无标题 + 6 层嵌套 + 77 屏」三者叠加，是全站最严重的阅读体验问题，**严重程度高于行宽**。

**具体数值建议**：
1. **补 h2**：按 YAML 顶层键（`anticheat`、`chunks`、`entities`、`environment`…）生成 h2；子键生成 h3。这是内容层改动，但 `headingScale.counts.h2=0` 说明构建流程把标题吃掉了，应查 `build-site.js` 的标题映射。
2. **限缩进**：`ul` 的 `padding-left` 在 `li` 嵌套 ≥3 层时收窄到 **1em（16px）**，或对深层用 `list-style-position:inside`。目标：6 层累计 ≤ **96px**（而非 144px）。
3. 页高本身不是问题（长文就该长），问题是**不可扫描**。

### §10 中文排版细节（CJK typography）

**测量值**：

| 项 | 实测 |
|---|---|
| 中英混排空格 | `world-configuration` 中「中文紧邻拉丁」**19 处**、「有空格」1 处；`dialogs` 3 处 / 2 处；`/paper/` 1 处 / 0 处 |
| 字体栈落点 | `-apple-system, …, "Noto Sans SC", "Microsoft YaHei", …`；`信` 宽 15.2px（≈full-width），`M` 宽 13.65px |
| `overflow-wrap:anywhere`（`.article`, `site.css:194`） | **1440 与 390 下正文词中断 0 次**；关闭后也 0 次，文档宽度不变（1440→1440） |
| 320 下正文词中断 | 1 处（`notice-type`，含连字符，属正常断点） |
| 代码/表格内词中断（390） | **10 处**；320 下 **19 处**（如 `DialogAfterAction` 断成 3 行、`AsyncPlayerConnectionConfigureEvent`） |
| 孤字（末行 <1.6 全角） | `dialogs` 31 段中 3 段（9.7%）；`world-configuration` 30 段中 1 段（3.3%） |

**基准**：中英混排宜在汉字与拉丁/数字间加 **1/4 em 空隙**（可用空格或 `text-spacing`）；英文单词不得在无连字符处断开；孤字率宜 < 5%。

**判定：疑。**
- **`overflow-wrap:anywhere` 的指控不成立**（见 §0.5）。它在正文里是**安全网**，实测未触发；真正被切断的是**代码块与表格单元格**（390 下 10 处、320 下 19 处）——那是 `<td>` 与 `<code>` 的自然换行，可接受（代码长标识符必须能断，否则横向溢出）。
- **真正的 CJK 问题是中英混排无空隙**：`world-configuration` 19 处「汉字紧贴拉丁」，读起来像「Paper源结构」「共103篇」。这是**内容生成层**（`build-site.js` 拼接模板）造成的，不是 CSS 能单方面解决，但可用 `text-spacing-trim` / 手动插入细空格缓解。
- 孤字率 9.7% 略高（`dialogs`），但中文孤字观感远好于西文，属可接受。

**具体数值建议**：① 构建时在 `汉字↔拉丁` 边界插入 `U+2009`（thin space）或普通空格；② `overflow-wrap:anywhere` **保留**（它是防溢出的安全网，实测无害）；③ 若想更严谨，正文用 `overflow-wrap:break-word`（只在必要时断）+ 代码块保留 `anywhere`。

### §11 一致性（cross-page consistency）

**测量值**：

| 页面类型 | 正文列宽 | ch | 正文字号/行高 | H1 字号/行高 | H2 字号 |
|---|---|---|---|---|---|
| 落地页 `/` | 949 | 110 | **16.8 / 28.56** | **32 / 54.4** | 21.6 |
| 分区页 `/paper/` | 949 | 110 | 16 / 27.2 | 28.8 / 36 | —（无 h2） |
| 正文页（有 TOC） | 849 | 98.4 | 16 / 27.2 | 28.8 / 36 | 22.4 |
| 清单页 `/all-pages.html` | 949 | 110 | 15.2（仅说明段） | **29.6 / 37** | — |

**判定：疑。** 四处不一致：
1. **落地页正文 16.8px vs 其余 16px**（`.hero-tag{font-size:1.05rem}` 与 `.hero p` 继承链导致）。5% 差异肉眼可辨，且落地页是「第一印象页」。
2. **H1 三套值**：32px（落地页 `.hero h1`）、29.6px（清单页）、28.8px（正文页/分区页）。同语义不同规格。
3. **H2 两套**：21.6px（落地页 `.hero` 内 h2）、22.4px（正文页）。差 0.8px，无理由。
4. **正文列宽两套**：949 vs 849（有无 TOC），差 100px，同一「正文」概念两种度量。

**具体数值建议**：统一到 **16px / 1.7** 一套正文；H1 统一 **2rem(32px) / 1.35**；H2 统一 **1.5rem(24px)**；正文列宽由 §4 方案统一为 **40rem**（有无 TOC 都一样，TOC 只是右栏附加）。

### §12 主题切换后的排版（post-theme-switch typography）

**测量值**：

| 项 | light | dark | auto+深色 |
|---|---|---|---|
| 正文对比度 | 16.49 | 14.76 | 14.76 ✓ |
| 代码 token 最低 | **3.87 ✗** | 5.76 ✓ | **2.85 ✗** |
| `--code-bg` vs `--bg` | 1.03 | 1.04 | 1.04 |
| 代码块边框 vs 底 | 1.22 | 1.35 | 1.35 |
| 面板（bg-soft/bg-elev）可见度 | 1.06 / 1.11 | 1.06 / 1.16 | 同 dark |

**判定：劣（auto 路径）/ 良（light、dark 各自）**。
- **light 与 dark 各自都是「可用的」**，dark 的代码高亮甚至优于 light（最低 5.76 vs 3.87）。
- **auto 是坏的**：底色切深、token 不切，7 个采样 token 全失败。这是**三条路径里唯一一条默认路径**（`<html data-theme="auto">`，见 `index.html:1`），也就是说**系统开了深色的用户，默认看到的就是最差的那套**。
- **dark 下代码块边界弱**：`--code-bg #171a1f` vs `--bg #14161a` = 1.04:1，仅靠 1.35:1 的边框区分。深色屏上这几乎不可见（截图对比可见代码块与正文区几乎连成一片）。

**具体数值建议**：① auto 补丁（见 §6，已实测修复）；② dark 下把 `--code-bg` 提到 `#1c2129`（1.12:1，仍克制）或把 `--border` 提到 `#39404d`（约 2.0:1）；③ light 的 8 个 token 修色（见 §6）。
